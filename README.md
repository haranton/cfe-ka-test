# CI расширения 1С на постоянной тестовой базе

После push GitHub Actions загружает расширение в уже существующую тестовую базу, обновляет конфигурацию БД, выгружает готовый CFE и выполняет включённые в конфиге тесты. После успеха создаётся PR в main для ручного ревью.

База остаётся после сборки со всеми данными и последним загруженным расширением. CI не создаёт базы, не загружает основную конфигурацию и не удаляет базу.

## Один конфиг

Все настройки проекта находятся в [ci/config.json](ci/config.json):

```json
{
  "platformVersion": "8.3.27.1936",
  "database": {
    "connection": "/F%USERPROFILE%\\OneDrive\\Документы\\vanessa",
    "user": ""
  },
  "extension": {
    "name": "MyExtension",
    "source": "cfe"
  },
  "tests": {
    "enabled": false,
    "command": "vrunner",
    "arguments": [
      "test", "vanessa",
      "--feature-path", "features",
      "--report-format", "junit",
      "--report-path", "%ONEC_CI_REPORTS%"
    ]
  }
}

```

Значение database.connection в конфиге репозитория пока оставлено пустым: укажите свою постоянную тестовую базу перед запуском.

| Настройка | Что указать |
|---|---|
| platformVersion | Установленную на runner версию платформы 1С |
| database.connection | /F<каталог базы> либо /S<сервер>\<имя базы> |
| database.user | Пользователя 1С; пустая строка для базы без аутентификации |
| extension.name | Имя расширения в базе |
| extension.source | Относительный путь к папке XML или готовому файлу .cfe внутри проекта |
| tests.enabled | true для запуска тестов, false для одной загрузки и выгрузки расширения |
| tests.command | Исполняемую команду тестирования |
| tests.arguments | Массив аргументов команды тестирования |

Строки могут содержать переменные Windows в виде %USERPROFILE%. Пароль передаётся через GitHub Actions Secret ONEC_DB_PASSWORD, локально — через переменную VRUNNER_DBPWD. Имя пользователя можно также передать через Secret ONEC_DB_USER.

Если настройки базы должны храниться только на компьютере runner, сохраните один такой же JSON вне рабочего каталога Git и задайте Actions Variable ONEC_CI_CONFIG с полным путём к нему. Скрипт использует этот файл целиком вместо ci/config.json; объединения нескольких конфигов нет.

## Запуск

GitHub Actions запускает ci/build.ps1. Вручную из корня проекта:

```powershell
# Проверить конфиг и существование файловой базы без её изменения.
.\ci\build.ps1 -ValidateOnly

# Загрузить расширение и выполнить включённые проверки.
.\ci\build.ps1

# Использовать конфиг, хранящийся на компьютере runner.
.\ci\build.ps1 -ConfigFile 'C:\1C-CI\config.json'

```

Скрипт выполняет две команды Vanessa Runner:

1. vrunner cfe load — загрузка XML или CFE и обновление расширения в постоянной базе.
2. vrunner cfe unload — сохранение установленного расширения в CFE для скачивания.

Для XML создаётся только копия файлов в build/<номер>/source, поскольку 1С обновляет ConfigDumpInfo.xml при загрузке. Это папка исходников, а не информационная база.

## Тесты

Тесты выключены по умолчанию. Команда в примере — запуск Gherkin-сценариев Vanessa-ADD. Для её включения добавьте реальные .feature в features и установите Vanessa-ADD на runner: opm install add. Затем переключите tests.enabled на true.

Для другого набора тестов укажите свою команду и её аргументы. Например, oscript со скриптом тестирования или powershell.exe с аргументами -File и путём к вашему .ps1.

Команда запускается из корня проекта и наследует VRUNNER_IBCONNECTION, VRUNNER_V8VERSION, VRUNNER_EXTENSION_NAME и реквизиты пользователя. ONEC_CI_REPORTS указывает каталог отчётов текущего запуска. Команда должна ждать окончания тестов и возвращать ненулевой код при их ошибке.

## GitHub Actions и ревью

Задание build_1c выполняется на зарегистрированном в репозитории Windows runner. Все ветки используют одну очередь: выполняется одна сборка, остальные ждут. Уже выполняющаяся загрузка не отменяется новым push.

В Actions сохраняются CFE, логи, отчёты и build-result.json со статусом и SHA коммита. При ошибке остаются логи и отчёты, новый PR не создаётся. В существующем PR проверка нового коммита становится красной.

После успешной сборки рабочей ветки PR создаёт GitHub Actions bot; владелец репозитория запрашивается как reviewer. Повторные push обновляют тот же PR. Для main требуется успешный build_1c, актуальный main в ветке и одно одобрение. Новые коммиты снимают предыдущее одобрение. Слияние выполняется вручную.

Агент ITSM создаёт ветку от актуального main и отправляет её в этот репозиторий. Если агент работает в другом GitHub workflow, push должен выполняться через GitHub App token или подходящий PAT; push через встроенный GITHUB_TOKEN не запускает следующие workflow. Также доступен ручной Run workflow.

## Перенос проекта

1. Перенесите XML расширения и файлы ci/.github в новый GitHub-репозиторий.
2. Подключите Windows runner к новому репозиторию, установите платформу, OneScript и Vanessa Runner. Для тестов установите выбранный тестовый инструмент.
3. В едином конфиге измените подключение к существующей тестовой базе, версию платформы и имя/источник расширения.
4. При необходимости задайте Secrets ONEC_DB_USER/ONEC_DB_PASSWORD и Variable ONEC_CI_CONFIG.
5. Разрешите GitHub Actions создавать pull request и настройте защиту main с проверкой build_1c и одним одобрением.
6. Выполните ValidateOnly, затем запустите workflow.

На текущем компьютере установлен runner в %USERPROFILE%\actions-runner-cfe-ka-test. После перезагрузки он запускается вручную:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\ci\start-runner.ps1

```
