# Сборка расширения 1С через GitHub Actions

Репозиторий предназначен для XML-исходников расширения из папки `cfe` и файлов CI. Основная конфигурация не хранится в этом репозитории.

После push ветки задачи GitHub Actions получает конкретный коммит, собирает расширение в отдельной файловой базе 1С и сохраняет `.cfe` и логи. После успешной сборки создаётся pull request в `main`. Слияние выполняет владелец репозитория после ревью.

Workflow: `.github/workflows/build-cfe.yml`. Скрипт сборки: `ci/build.ps1`. Имя расширения, папка XML и версии инструментов задаются в `ci/build-settings.json`.

## Последовательность

1. Агент создаёт ветку от актуального `main`, изменяет XML-исходники и отправляет коммит в GitHub.
2. Задание `build_1c` создаёт новую базу для каждого запуска.
3. В базу загружается эталон основной конфигурации с компьютера runner, затем XML-исходники расширения из коммита; конфигурация БД обновляется.
4. Из собранной базы выгружается `.cfe`.
5. GitHub сохраняет логи, файлы поставки и сведения о коммите.
6. Для успешной ветки открывается pull request. Повторные push обновляют ту же ветку и повторяют сборку.
7. Владелец проверяет изменения и результат сборки, одобряет PR и вручную объединяет его с `main` либо закрывает PR.

В первой версии выполняется сборка без модульных и сценарных тестов. Успешный статус подтверждает создание файлов поставки и обновление конфигурации БД.

## Окружение сборки

GitHub Actions runner — приложение на компьютере, которое получает задания из GitHub и выполняет команды workflow. Vanessa Runner — установленная на этом компьютере утилита, выполняющая операции платформы 1С.

Используется self-hosted Windows runner `ANTON-cfe-ka-test` с меткой `onec-cfe-ka-test`. На компьютере установлены платформа `8.3.27.1936`, OneScript `2.2.0` и Vanessa Runner `3.0.2`.

GitHub Actions runner установлен в версии `2.337.0`. Первая сборка в GitHub завершилась успешно: [запуск на main](https://github.com/haranton/cfe-ka-test/actions/runs/37381039147).

Эталон основной конфигурации хранится вне Git-репозитория на runner в виде `.cf` или шаблона базы. Для каждого запуска фиксируются версия и контрольная сумма эталона. Путь к нему задаётся в настройках CI. При переходе на расширение другой конфигурации эталон нужно заменить на совместимую основную конфигурацию.

Текущий сценарий принимает эталон `.cf`. В GitHub Settings → Secrets and variables → Actions → Variables настроены `ONEC_BASELINE_CF` (локальный путь на runner) и `ONEC_BASELINE_SHA256` (SHA256 файла). При изменении эталона нужно обновить обе переменные.

Первый эталон собран из локальной учебной конфигурации «Конфигурация» для расширения `MyExtension`. Это не эталон типовой «Комплексной автоматизации»; для расширения КА нужен соответствующий файл основной конфигурации.

Каждая сборка использует собственную базу. База разработки и общая пользовательская тестовая база не используются для сборки веток.

Платформа получает копию XML-исходников: обновление служебного `ConfigDumpInfo.xml` не меняет файлы Git. База удаляется после завершения сборки. В GitHub публикуются файл расширения и логи, сама база не загружается.

Runner установлен в `%USERPROFILE%\actions-runner-cfe-ka-test` и выполняется в фоне от текущего пользователя. Компьютер должен быть включён. После перезагрузки или выхода из Windows runner запускается вручную:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\ci\start-runner.ps1
```

## Локальная сборка

```powershell
$baseline = Join-Path $env:USERPROFILE 'actions-runner-cfe-ka-test\baselines\Configuration.cf'
$hash = (Get-FileHash -LiteralPath $baseline -Algorithm SHA256).Hash
.\ci\build.ps1 -BaselineFile $baseline -BaselineSha256 $hash
```

Результаты записываются в `build/<номер-запуска>/`. Папка `build` исключена из Git. Для ручного запуска в GitHub откройте Actions → Сборка CFE → Run workflow и выберите ветку.

## Связь с агентом ITSM

Агент сохраняет номер задачи, имя ветки и SHA отправленного коммита. Статус сборки читается для этого SHA. Артефакты и ссылка на PR доступны в GitHub Actions.

Ветка задачи должна включать файл workflow из актуального `main`. Push должен создавать события GitHub Actions: встроенный `GITHUB_TOKEN` другого workflow не запускает workflow по событию push; для такого агента нужен GitHub App token, подходящий PAT либо явный dispatch.

Пример отправки ветки после изменения исходников:

```powershell
git switch main
git pull --ff-only
git switch -c itsm/ITSM-123
# Здесь агент изменяет исходники расширения в папке cfe.
git add cfe
git commit -m "ITSM-123: доработано расширение"
git push -u origin itsm/ITSM-123
```

Ручной запуск workflow для ветки задачи также создаёт PR после успешной сборки. Если PR уже открыт, повторный запуск сохраняет существующий PR.

## Ревью

Для `main` требуется успешное задание `build_1c` и одно одобрение. При новых коммитах предыдущее одобрение снимается. Автоматическое слияние не выполняется.

Ветка должна включать актуальный `main`. Если другая задача уже объединена, агент добавляет изменения `main` в свою ветку и повторяет push, чтобы сборка проверила обновлённый код.

Workflow сборки запускается для push внутри этого репозитория. События pull request из внешних forks не запускают локальную сборочную машину.

## Артефакты

- Файл расширения `.cfe`.
- Логи отдельных операций 1С.
- Манифест со статусом, SHA коммита, версиями инструментов и контрольными суммами файлов поставки.

Файлы поставки публикуются после успешной сборки. Логи сохраняются также при ошибке. Создание PR выполняется отдельным заданием после сборки.
